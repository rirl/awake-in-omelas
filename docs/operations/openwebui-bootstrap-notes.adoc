== Filesystem MCP Server

=== Standalone Validation

Read-only validation command:

[source,bash]
----
docker run --rm -it \
  --name Omelas-MCP-RO \
  --read-only \
  --security-opt no-new-privileges:true \
  -p 127.0.0.1:8765:8000 \
  -v /home/landonr/projects/awake-in-omelas:/workspace/omelas:ro \
  mcp/filesystem:latest \
  /workspace/omelas
----

Observed output:

[source,text]
----
Secure MCP Filesystem Server running on stdio
Allowed directories:
    /workspace/omelas
----

Observation:

The filesystem MCP server communicates over stdio and therefore cannot be
consumed directly by Open WebUI.

== MCPO Bridge

=== Purpose

MCPO bridges the stdio-based filesystem MCP server to an HTTP/OpenAPI endpoint
that can be consumed by Open WebUI.

=== Validated Launch Command

[source,bash]
----
uvx mcpo \
  --port 8765 \
  -- \
  docker run --rm -i \
    --name Omelas-MCP-RO \
    --read-only \
    --security-opt no-new-privileges:true \
    -v /home/landonr/projects/awake-in-omelas:/workspace/omelas:ro \
    mcp/filesystem:latest \
    /workspace/omelas
----

NOTE:

The Docker container is launched with `-i`, not `-it`, when executed under
MCPO.

=== Architectural Observation

An important architectural observation emerged during validation.

The existing Filesystem MCP launch scripts required no modification to support
Open WebUI.

Instead, MCPO functions as an adapter between the stdio-based Filesystem MCP
server and HTTP/OpenAPI clients.

This preserves the Filesystem MCP server as the canonical implementation while
allowing multiple client technologies to consume the same service through
protocol-specific adapters.

This architectural separation reinforces the principle that stable platform
capabilities should remain protocol-independent wherever practical.
