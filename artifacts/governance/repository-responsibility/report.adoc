== Repository Identity

The *awake-in-omelas* repository is the canonical governed repository for the
Awake in Omelas project.

Its long-term responsibility is to preserve and evolve the project's
authoritative domain artifacts, governance artifacts, architectural decisions,
validation evidence, and implementation that are intrinsic to the project
itself.

Following completion of Breakpoint Beta, portions of the repository are
expected to have transitioned into reusable infrastructure whose continuing
architectural ownership no longer belongs within the Awake in Omelas project.

This Repository Responsibility Assessment (RRA-0001) establishes the
authoritative repository boundary after completion of that transition.

The assessment serves as the execution record supporting future repository
promotion activities and defines which artifacts remain canonical
responsibilities of the repository and which should instead become the
responsibility of other repositories or external operator-managed state.

== Purpose

The purpose of this assessment is to determine whether every artifact currently
contained within the repository continues to belong to the architectural
responsibility of the Awake in Omelas project.

Specifically, the assessment seeks to:

* identify the continuing architectural owner of each repository artifact;
* distinguish project-specific assets from reusable infrastructure;
* identify operator-managed artifacts that should not be maintained in Git;
* support repository promotion following Breakpoint Beta;
* provide documented justification for future artifact migration or removal;
* establish an auditable record of repository responsibility decisions.

This assessment is intended to become the canonical responsibility evaluation
for the repository following completion of Breakpoint Beta.

== Scope

This assessment applies only to the contents of the active
`awake-in-omelas` repository.

The assessment includes:

* repository structure;
* governance artifacts;
* documentation;
* implementation artifacts;
* validation artifacts;
* scripts;
* templates;
* canonical project knowledge.

The assessment excludes:

* confidential operator state;
* local runtime configuration;
* private deployment artifacts;
* Docker runtime state;
* externally managed infrastructure;
* implementation correctness;
* code quality;
* software testing.

No repository restructuring is performed by this assessment.

The assessment records responsibility only.

== Objectives

The objectives of RRA-0001 are:

. establish the authoritative architectural boundary of the repository;
. determine continuing ownership for all major artifact classes;
. identify reusable infrastructure suitable for extraction;
. identify artifacts that should become operator-managed;
. document repository promotion recommendations;
. preserve complete assessment provenance;
. support future repository governance activities.

Success is achieved when every assessed artifact can be assigned an explicit
continuing architectural responsibility.

== Governing Principles

This assessment is governed by the following principles.

=== Architectural Responsibility

Artifacts should reside within the repository whose long-term architectural
mission they support.

=== Single Continuing Owner

Every governed artifact shall possess one continuing architectural owner.

Repository boundaries shall reflect responsibility rather than historical
origin.

=== Canonical Knowledge Preservation

Project-specific knowledge shall remain within the project repository even when
supporting implementation is extracted elsewhere.

=== Separation of Reusable Infrastructure

Infrastructure intended for reuse across multiple repositories should migrate
to a dedicated infrastructure repository once sufficient independence has been
demonstrated.

=== Separation of Operator State

Operator-specific configuration, runtime state, secrets, deployment metadata,
and similar operational artifacts shall remain outside the governed project
repository unless intentionally preserved as governance evidence.

=== Evidence-Based Assessment

Repository responsibility decisions shall be supported by collected evidence
rather than assumptions.

== Assessment Method

The assessment follows an evidence-driven architectural review.

The methodology consists of:

. inventory the repository;
. collect objective repository evidence;
. classify artifacts according to architectural role;
. determine continuing ownership;
. identify architectural boundary crossings;
. recommend promotion, extraction, retention, or removal where appropriate;
. record findings for future governance activities.

The assessment intentionally distinguishes between:

* historical implementation origin;
* current repository location;
* continuing architectural responsibility.

Only continuing responsibility determines the recommended repository boundary.

== Repository Responsibility Model

The responsibility model classifies repository contents according to their
continuing architectural ownership.

Primary responsibility categories include:

Project Responsibility::
Artifacts intrinsic to the Awake in Omelas project and expected to remain
within the repository.

Reusable Infrastructure::
Artifacts whose continuing value extends beyond the project and are candidates
for extraction into shared infrastructure repositories.

Governance Evidence::
Artifacts preserved to document governance decisions, validation activities,
architectural history, or assessment outcomes.

Operator State::
Artifacts whose ownership belongs to deployment or operational environments and
therefore should remain external to the governed repository.

Historical Preservation::
Artifacts intentionally retained to preserve engineering provenance even after
their operational role has concluded.

This responsibility model provides the basis for all subsequent assessment
findings.

== Promotion Recommendations

The following repository components are recommended for promotion into
independently governed repositories where their architectural
responsibility extends beyond the Awake in Omelas project.

=== PR-001 — Governed MCP Runtime

Components implementing reusable governed execution infrastructure,
including launcher mechanisms, runtime policy enforcement,
MCPO integration, Filesystem MCP support, container runtime
management, and reusable execution libraries, should be maintained
within the `governed-mcp-runtime` repository.

Benefits include:

* Independent lifecycle management.
* Reuse across multiple governed repositories.
* Reduced coupling between project content and execution framework.
* Clear architectural ownership.

=== PR-002 — Reusable Governance Mechanisms

Generic governance mechanisms developed during repository evolution
should be evaluated for future extraction into technology-independent
governance repositories where appropriate.

Examples include:

* repository assessment methodology;
* generalized evidence collection patterns;
* reusable governance templates; and
* repository lifecycle guidance.

Extraction should occur only after individual mechanisms have
demonstrated stability through practical application.

=== PR-003 — Preservation Artifacts

Immutable engineering evidence generated during major architectural
milestones should remain preserved within dedicated preservation
repositories rather than duplicated inside the active project
repository.

The active repository should instead reference those preservation
packages where historical traceability is required.

== Removal / Relocation Recommendations

The assessment identified several categories of artifacts whose
continuing responsibility lies outside the Awake in Omelas repository.

=== RR-001 — Operator State

Operational state, credentials, deployment secrets, runtime caches,
generated configuration, local deployment metadata, and similar
environment-specific information should remain outside version control
and be managed through designated operational repositories or runtime
management systems.

=== RR-002 — Generated Runtime Artifacts

Files generated automatically during execution should not be retained
as permanent repository contents unless they represent canonical
engineering evidence approved for long-term preservation.

Examples include:

* temporary execution logs;
* generated cache contents;
* intermediate build outputs;
* transient container state; and
* disposable validation outputs.

=== RR-003 — Deployment Configuration

Machine-specific deployment configuration should remain external to the
repository wherever practical.

Repository documentation may describe deployment expectations, but
environment-specific implementation details should remain under
deployment management.

=== RR-004 — Reusable Runtime Infrastructure

Reusable execution infrastructure should continue migrating toward the
dedicated governed runtime repository, allowing Awake in Omelas to
focus exclusively upon project knowledge, governance, validation, and
canonical content.

== Dependency Assessment

The repository demonstrates a clear architectural dependency hierarchy.

Awake in Omelas remains the authoritative source for project-specific
governance, documentation, validation, and narrative content.

Reusable execution infrastructure has been intentionally separated into the
governed-mcp-runtime repository. This establishes a reusable implementation
boundary that can support multiple governed projects without introducing
cross-project coupling.

Engineering preservation artifacts similarly form an independent concern and
belong within the preservation repository, ensuring that historical evidence
remains immutable while operational repositories remain focused on current
development.

The assessment found no architectural dependency that requires the Awake in
Omelas repository to permanently retain reusable runtime infrastructure or
historical preservation packages.
